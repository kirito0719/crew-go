# ISSUE-100 · AutoCompact 并发历史边界

已修复，2026-11-23。跨 Run 的压缩边界只能覆盖摘要实际读取的历史前缀，以及同一次调用随后写入且已纳入视图的记录。

## 复现

同一租户、会话与成员位置内，A 生成摘要并阻塞在主模型调用。B 完成并提交问答，随后 A 完成。修复前，原始历史里依次有 B 的问题、B 的答案和 A 的答复，C 的首次请求却只收到 A 的答复。回归通过两个通道控制提交顺序，同时检查原始历史与 C 的实际模型输入。[并发、嵌套与断点恢复回归](../../agent_v2/compaction_boundary_test.go)

## 来源与写入顺序

```text
A 的 preamble             异步历史写入器            同会话的后端
读取未过滤的会话尾游标  ←───────────────────────── 当前尾行
读取本成员视图
提交本次调用的普通记录  →  按预期尾游标追加  ──────→ 成功后返回新尾游标
B 完成并追加问答         ─────────────────────────→ 会话尾部变动
A 提交摘要候选与答复    →  预期尾游标已过期  ──────→ 整批条件追加被拒
                         去掉候选，追加普通记录 ───→ B 的问答、A 的答复
```

- 每次编译的 BasicAgent 图独立持有来源。子成员即使共享写入队列，也各自从自己的历史读取位置开始。读失败、使用自定义历史压缩器、实际触发轮数裁剪，或直接从存档恢复到模型节点时，沿用普通追加与 Run 内压缩。
- 条件追加成功时，后端把证明绑定到该批次的具体行。下次读取同时检查成员、视图、位置和替代历史。旧边界或通过普通追加导入的副本没有位置证明，读取会继续向前。重复消息 ID 不参与尾游标判断。
- 确定失配时普通记录照常进入历史。提交回执不确定时，当前批次按历史层原有错误策略处理，后续普通记录继续追加，本次调用放弃候选边界。调用方前文按专有的去重规则处理，边界之后抵达的新前文仍会进入三种视图。
- 内存后端在会话存储锁内执行比较与追加。SQL 后端在事务中锁定同一会话的写入行，再读取尾游标和追加。已存在的历史行无需改写。升级 SQL 服务时先排空旧写事务，运行 `HistoryStore.Setup` 后统一切换写入端。SQL 把证明绑定到 INSERT 实际返回的主键，复制原始 payload 到另一行会得到普通记录。PostgreSQL 分配新行时跳过连接缓存中早于会话尾部的序号。条件追加的区间若含同表触发器额外写入的行，事务回滚，写入器再追加普通记录。[升级说明](../release/next.md)

普通自定义 HistoryStore 可继续提供跨 Run 原始历史。要复用跨 Run 摘要，存储需显式实现 `HistoryTailAppender`，包装器需同时承接普通和条件写入。Folio 式 ContextRecovery 保持单 Run 折叠与按需取回。[历史能力契约](../../agent_v2/history.go) · [一致性套件](../../agent_v2/history_conformance/conformance.go) · [上下文恢复](../v2/context-recovery.md)


## 验证

生产 BasicAgent 回归覆盖 A/B/C 并发、嵌套共用写入器、序列化 Resume、裁剪过的 prior、丢失提交回执、重复消息及三种视图中的晚到前文。隔离撤掉源水位核对后，C 的首次请求再次只剩 A 的答复。SQL 在 SQLite、PostgreSQL 16.9 和 MySQL 8.0.33 上验证，另覆盖 PostgreSQL 两个连接使用 `CACHE 8` 交替追加、SQLite 批内回滚、复制原始 payload 和触发器追加。[SQL 回归](../../sql/history_test.go) · [真实数据库集成](../../sql/conformance_integration_test.go)
